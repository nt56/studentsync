# Running and maintaining StudentSync

Updated November 12, 2026 (Phase 4). This guide explains how to run StudentSync, its email worker, and its maintenance tools.

## MongoDB requirement

**Project constraint:** one plain standalone `mongod`. No replica set, no backup database, no secondary members, and no second copy of the data. The app needs nothing else: it uses no transactions or sessions, and both Compose files run a plain `mongo:7`.

Development and production Compose are separate stacks with separate volumes. Run only the stack you intend to use; starting both would create two independent application databases. Development: `docker compose up -d --build`. Production: `docker compose -f docker-compose.prod.yml up -d --build` (requires `MONGO_PASSWORD`; if it contains URI-reserved characters, use a properly encoded runtime connection URI).

Connection strings carry no replica-set options: `mongodb://mongo:27017/studentsync` inside Compose, `mongodb://127.0.0.1:27017/studentsync` from the host. The development MongoDB port is bound to loopback only.

**Upgrading a database that ran the earlier single-member `rs0` setup:**

1. Stop the app and workers. Keep the `mongo-data` volume; do **not** run `docker compose down -v`.
2. Start the new Compose stack. MongoDB starts as a standalone on the existing data; the unused `rs0` metadata in the `local` database is harmless. The old `mongo-keyfile` volume is no longer used and may be removed.
3. Run `npm run db:backfill-seats` once. It sets `Event.registeredCount` from the real registrations. (The worker would also do it within minutes, and the first registration or capacity edit on an uncounted event counts it on demand, but running it up front avoids surprises.)
4. Start the app. Verify login, registration, an event edit, and the outbox on a disposable event.

## Write safety without transactions

Every mutation is built from single-document atomic operations, unique indexes, and idempotent writes. Where one request needs several writes, the order is fixed so that a crash between any two of them leaves a state a background pass repairs.

- **Seats.** `Event.registeredCount` is the seat counter. Registration reserves a seat with a conditional `$inc` (only while `registeredCount < capacity`; zero matches means full), then inserts the registration (unique `{eventId, studentId}`), and gives the seat back if the insert fails. Cancelling claims the row (`cancelling`), queues its follow-ups, deletes the row, and releases the seat only if that delete removed something. The seat stays held until then, and the worker finishes a claim that a crash left behind. Lowering capacity is a conditional update (`registeredCount + heldCount <= newCapacity`), so it cannot race a registration or a waitlist offer below the seats taken or held.
- **Waitlist.** `Event.heldCount` counts seats held for open offers, so a free seat means `registeredCount + heldCount < capacity`. Every `WaitlistEntry` status change is one conditional update that claims a single transition, and only the winner touches a counter. An offer first takes a hold (conditional `$inc heldCount`), then claims the oldest `waiting` entry; with no entry left it gives the hold back. Accepting claims `offered → accepted` (with `acceptPending`), turns the hold into a taken seat in one `$inc`, then inserts the registration. Declining or expiring claims the transition, releases the hold, and offers the seat to the next student. Before a claim that is followed by a counter change, the request bumps `seatsTouchedAt` so the reconciler cannot rewrite the counters in that gap. The worker expires offers after 12 hours (never later than the registration deadline), closes queues at the deadline, re-sends offer notices still marked `offerNoticePending`, finishes accepts still marked `acceptPending`, and offers any free seat to the queue (this also covers capacity increases and promotions a crash lost). While anyone is `waiting`, direct registration is refused so the queue keeps priority; a student holding an offer who calls `POST /api/registrations` accepts it.
- **Reconciler.** The worker compares every counter with the real registrations (and `heldCount` with the open offers) about every five minutes and repairs differences. It only touches counters that have been quiet for 60 seconds and updates with compare-and-set, so it never overwrites a seat change in flight. A crash between reserve and insert therefore heals itself.
- **Side effects.** Notifications and email jobs carry a deterministic `dedupeKey` backed by a unique index. A duplicate-key error means "already queued". A new registration carries `effectsPending` until its notifications and confirmation email are queued. Role changes and event edits write a notice marker (`pendingRoleNotice`, `updateNotice`) in the same atomic update as the change. The worker finishes anything still marked after 30 seconds, so a crash after the main write loses nothing.
- **Event deletion.** One atomic write marks the event `deleting`, which hides it from every user-facing query. The cleanup (cancellation emails, then registrations, reviews, bookmarks, chat, collaborations, announcements, waitlist entries, and finally the event) is idempotent. The request runs it inline and the worker re-runs it for any event stuck in `deleting`.
- **Collaboration accept.** The response is claimed with a conditional `pending -> accepted` update; the partner college and editor membership are idempotent follow-ups. Repeating the same response after a crash completes them.
- **Role changes.** The Better Auth identity is written first, then the application profile (which every permission check reads), so a crash never grants privileges early. Repeating the request completes it, and `db:audit` reports any identity/profile mismatch.
- **Account deletion (admin).** The login identity goes first, the profile last, open waitlist offers are declined (their seats go to the next student), and each registration's seat is released only by the delete that removed it. A retry finishes the remaining steps.
- **Account deletion (self-service).** `DELETE /api/users/me` first sets `User.deletion.requestedAt` (from then on `requireAuth` refuses the profile), then removes push devices, the login identity, sessions, and linked accounts, then the personal records (upcoming registrations with their seats, waitlist entries, bookmarks, notifications, queued email and push jobs, saved searches, collaborations, staff roles, reports, reviews with a rating rebuild, and chat text). It anonymizes the profile last (`deletedAt`, "Deleted user", `deleted-<id>@deleted.invalid`), so past events and past attendance keep a valid owner. The worker finishes any deletion still marked after 60 seconds. Owned events that have not ended block the request; it re-checks after setting the marker, so an event created at that moment still blocks. Admin accounts cannot delete themselves. `db:audit` skips anonymized profiles, which intentionally have no login identity.
- **Push devices.** `DeviceToken` is unique per Expo token and records the Better Auth session that registered it. Signing out deletes the session's devices; delivery also drops devices whose session has gone or expired. Registering the same token from another account moves it.
- **Offline tickets.** A ticket is the signed check-in JWT for one registration. It expires 6 hours after the event ends (`lib/tickets.ts`). `Registration.qrToken` only caches the latest token, and a reschedule re-signs it on the next sync. Revocation is the registration itself: check-in refuses a cancelled or cancelling registration, and `GET /api/registrations/tickets` returns the full current set, so the app drops anything missing.
- **Drafts.** `Event.draft` is `true` only while unpublished; published and older events have no such field, so `{ draft: { $ne: true } }` (`publishedEvent` in `models/Event.ts`) treats them as public. Publishing is one compare-and-set update (`draft: true` → unset), so repeated or parallel publishes are harmless.
- **Announcements.** The daily cap is claimed with one conditional update on `Event.announcementLog` (the newest three send times; it matches only while fewer than three fall in the last 24 hours). The `Announcement` row is unique per `{eventId, requestId}`, so a retried request returns the original. It carries `fanoutPending` until every registrant's notification and email job (keys `announcement:<id>:<userId>` and `…:email`) is queued; the worker finishes any fan-out still pending after 30 seconds. A crash between the cap claim and the insert costs one slot for the day and sends nothing.
- **Saved-search alerts.** The worker matches events whose `publishedAt` is newer than each alert-enabled search's cursor (`alertsCheckedAt`, never before `alertsSince`), using the same filter builder as `GET /api/events` (`lib/event-filters.ts`). Drafts have no `publishedAt` and are excluded by `publishedEvent`, so they never alert. Each match queues the email job (`search-alert:<searchId>:<eventId>:email`), then the notification under `search-alert:<searchId>:<eventId>`, which is the "done" marker. The cursor trails each pass by 10 minutes so a publish that became visible late is still seen; the dedupe key makes the re-read harmless. Switching alerts on resets the window to "now", so no backlog is sent. The 10-per-student limit is a soft count check (two simultaneous saves can both pass it).
- **Audit log.** `AuditLog` is append-only: `lib/audit.ts` only inserts, every field is immutable in the schema, and no route updates or deletes entries. Role changes and account deletions write their entry **before** the first change (after the permission and existence checks). Admin deletions of events, messages, reviews, and colleges do the same. A crash after the entry leaves an entry whose change never finished, and repeating the request completes the change (and may add a second entry). Follow-up entries carry a unique `key`, so writing them again is a no-op.
- **Reports and college decisions.** Each decision is one conditional update that claims the transition and stores a random `key` with `pending: true`. Resolving a report claims every open report on the same content (`status: "open"` → `removed`/`dismissed`). A college decision claims "not already in that state". Two admins racing produce one winner. Keyed follow-ups then run: the audit entry, the removal (message `isDeleted`, review delete plus rating rebuild, or event → `draft: true` with `hidden`), and the notices (`report-resolved:<reportId>`, `college-decision:<key>`, `event-hidden:<key>`). After that, `pending` is cleared for that key only. The worker finishes anything still pending after 60 seconds, and repeating the request does the same.
- **Review totals.** `averageRating` and `reviewCount` are rebuilt after each review write, and the worker repairs them every five minutes if a crash or a race left them stale.
- **Sockets.** Broadcasts and room changes run right after the write that justifies them.

Recovery depends on the worker: keep it enabled in `server.ts`, or run `npm run worker` when `OUTBOX_WORKER_ENABLED=false`. The upgrade from `rs0` data files, `db:backfill-seats`, `worker --once`, and `db:audit` were exercised on a real `mongod` 7.0.14 binary; the Compose stacks themselves were only validated with `docker compose config`.

For historical partial changes, use the audit below. Missing event owners, absent login identities, and existing overbooking require an operator decision; the script reports them without deleting valid business records.

## Durable email and reminders

The custom `server.ts` runs a worker every 15 seconds. It persists upcoming-event reminders, runs the waitlist pass, matches new events against saved-search alerts, finishes interrupted registrations, cancellations, notices, announcement fan-outs, and event deletions, reconciles seat counters and review totals, and claims email jobs using an atomic 60-second lease. Email requests time out after 20 seconds; failures retry with exponential backoff, up to eight attempts. A crashed worker's expired lease can be reclaimed by another instance.

Set `OUTBOX_WORKER_ENABLED=false` if using a separate worker, then run `npm run worker`. `npm run worker -- --once` performs one cycle. Keep using the custom server so Socket.IO is available.

Configure `BREVO_API_KEY`, `BREVO_SENDER_EMAIL`, and optionally sender name/reply-to settings. Verify the sender with Brevo. Missing provider settings leave retryable jobs rather than pretending delivery succeeded. Admins see failed, waiting, and in-flight jobs with their `lastError` on **Dashboard → Email Delivery** (`/dashboard/delivery`). It also warns when the provider settings are missing. After correcting the cause, use **Retry** on a job or **Retry all failed**: the job goes back to `pending` with `availableAt` set to now and `attempts` reset to zero. Jobs being sent or already finished are never touched. This replaces editing the `outboxes` collection by hand. Each retry is recorded in the audit log.

**Push** uses the same outbox (`channel: "push"`), leases, retries, and health page. Jobs are queued only for users with a registered device, under the notification's key plus `:push`, for the 24-hour and 1-hour reminders, waitlist offers, and announcements. Just before sending, the worker re-checks the job against current data: it is skipped (with `skipReason`) if it has expired, push or reminders are switched off, the event is deleted, a draft, or rescheduled (reminders store the start time), the student is no longer registered, or the waitlist offer has closed. Pushes go through the Expo Push Service (`EXPO_ACCESS_TOKEN` is optional; `PUSH_ENABLED=false` stops queueing). Each accepted message gets a ticket; about 15 minutes later the worker fetches receipts, and `DeviceNotRegistered` (on the ticket or the receipt) deletes that token. Receipts that never appear are given up after a day. If no message was accepted because of a provider-side error, the job is retried like an email.

Delivery is **at least once**. If the provider accepts an email and the process crashes before saving success, a retry can deliver it twice. Successful/skipped job bodies are removed immediately, and finished records expire after seven days. Failed jobs remain available for investigation. Treat queued authentication links as sensitive database data.

Users can save reminder, nonessential-email, and mobile push preferences in Settings. Verification and password-reset emails bypass the email preference. Each registration gets two reminders: one 24 hours before the start (in-app plus a non-essential email) and one 1 hour before (in-app only). Each is written once its window opens and only until the next window starts, so a late registrant gets only the 1-hour reminder. The key is `reminder:<userId>:<eventId>:<24h|1h>:<start ISO>`; the email job is queued before the notification, and the notification marks the reminder done, so a worker restart re-runs the pass and writes only what is missing. Read/dismiss state is stored; dismissals are retained so polling does not recreate them. Rescheduling dismisses reminders written for the old start (`Notification.scheduledFor`) and the new start gets new keys; cancelling dismisses the student's reminders.

The private calendar feed (`/api/calendar/<token>.ics`) stores only a SHA-256 hash of its token on the user (`calendarFeed.tokenHash`, unique sparse index). Creating a link replaces the hash and revokes the previous link; revoking removes it. The feed lists registered events from the last 30 days onwards, is rate limited per IP when Redis is configured, and is served with `Cache-Control: private, no-store`.

## Dry-run audit and reviewed repair

This is optional maintenance, not a prerequisite for starting the next phase. The command intentionally does not load `.env`. Set `AUDIT_MONGODB_URI` explicitly to the intended existing database. Do not put credentials in a committed script.

```text
npm run db:audit -- --output data-audit.json
```

This writes a report and changes no records. Review its `issues` array; remove any proposed repairs you do not approve. The report contains database identity, IDs, and proposed actions, without the URI or user email addresses. It refuses to overwrite an existing report.

Only when intentionally applying reviewed repairs, with application writes and workers paused:

```text
npm run db:audit -- --apply --report data-audit.json --confirm-database studentsync
```

The URI fingerprint and database name must match the reviewed report. The script re-audits and repairs only matching approved IDs/actions; each repair is one idempotent write, so an interrupted run can be repeated. It can remove orphan child records, align login roles with application roles, backfill reviewed event times, rebuild review totals, and reset seat and held-seat counters from the real registrations and open waitlist offers. Missing authors on retained messages/reviews are valid historical records. `manual` findings are never automatically changed.

A committed repair has no automatic undo; the dry run is sufficient for inspection. Older events read with a two-hour end-time fallback and UTC when fields are absent. That is a compatibility assumption, not recovered historical information. Review proposed time backfills against the real event schedule before applying them.

## Validation

```text
npm test
npm run lint
npx tsc --noEmit
npm run build
```

The commands above do not create a test database. Separately, `npm run test:integration` starts a disposable plain standalone MongoDB 7 (no replica set) with synthetic data and a custom app server on port 3101 with a separate `.next-integration` build directory. Its first run downloads MongoDB. Set `INTEGRATION_MONGODB_URI` (the database name must start with `studentsync_integration`; it is dropped) to use an existing throwaway server instead, as CI does. It seeds signed Better Auth session fixtures, overrides external-service settings, disables email delivery, and cleans up its own processes/database. It never connects to or copies the `.env` database. The suite includes 8-way and 50-way seat races, a cancel/register race, a capacity-lowering race, and fault injection that breaks the sequence between writes and expects the reconciler to repair it. Phase 2 adds racing waitlist promotions and parallel accepts, offer expiry and decline, an interrupted accept and a leaked hold, separate 24h/1h reminders across a reschedule, the calendar feed's revocation, and schedule-conflict edge cases. Phase 3 adds recommendation exclusions (full, held, past, draft, joined) and ranking, saved-search ownership, uniqueness and limits, and alerts that skip drafts, send no backlog, and stay single across parallel worker passes. Phase 4 adds required reasons and audit entries for role changes, account deletions and admin deletions, a 405 on every write to the audit log, report deduplication including parallel duplicates, resolution of every report on the same content with one notice per reporter, message/review/event removal (a hidden event cannot be republished), parallel college decisions with exactly one winner, resolutions and decisions that heal in the worker after a simulated crash, and outbox retries that never touch sent jobs or return email bodies.

For browser fixtures, start `node --import tsx tests/start-preview.mjs`, then run `node tests/browser-smoke.mjs` and `node tests/socket-smoke.mjs`. The preview sets an isolated MongoDB URI on port 27099 but does not provision a database. Browser smoke tests intercept API responses with fixtures; the socket check verifies guest rejection. They do not establish that authenticated database flows work. Preview uses port 3100 and `.next-preview`; Chrome DevTools uses port 9231. `CHROME_PATH` overrides the browser executable. Screenshots go to ignored `tests/artifacts`. Browser checks cover keyboard focus, accessibility-tree names, pagination with 65 fixture users, mobile layout, settings, and reduced motion. These checks do not replace a human screen-reader usability session.
